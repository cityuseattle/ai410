What's the HOS?

HOS 4 (Hands-On Skill) is this module's main build and 10% of your course grade. It has four stages across the two weeks: Create / Scaffold and Evaluate in Week 7, then Analyze and Understand & Refine in Week 8. All four go in one GitHub repo, and you submit that repo's link once, in Brightspace, at the end of Week 8. The Muddiest Point, Concept Debate, Application Challenge and Knowledge Check are graded separately.

Three HOS in, your app reasons, retrieves, validates, and works in the background — and you can only see any of that from a browser tab and a terminal. This last HOS takes it to production shape. A mobile client puts the app on a real phone. Push notifications tell the user when background work finishes, even with the app closed. And observability lets you see what the agent actually did on every request, so "it gave a wrong answer" becomes a specific span you can open and fix.

Week 7 builds and tests all three. Week 8 is the last HOS week, and it does double duty: finish HOS 4, then step back and connect all four HOS in an architecture review and a final Integration Concept Debate — the bridge into your Term Project.

Anchoring analogy

Think of a package delivery service. The mobile app is the storefront in the customer's pocket. The push notification is the "your package has arrived" text — sent to a specific phone, not just a name. And observability is the tracking page: every scan at every depot, with a timestamp. When a package is late, nobody guesses; they open the tracking history and see exactly which depot held it. A trace is that tracking history for one request.

Learning objectives

By the end of the two weeks you will be able to:

  1. Connect a mobile client to an existing AI backend, and explain why the backend didn't need to change. O5
  2. Trace the push-notification chain end to end and diagnose which link failed when nothing arrives. O5
  3. Read a trace with nested spans and use it to locate a latency or quality problem. O4
  4. Evaluate the reliability of probabilistic outputs with a metric — faithfulness — and critique what it can and can't tell you. O4
  5. Explain the full path of a request across all 4 HOS and where it could slow down or fail. O4 O5

Part 1 — A mobile client for the same backend ≈ 5 min

Optional video2:39 · Fireship

A fast tour of what Expo is. Watch for "one JavaScript codebase, real iOS and Android apps" and for Expo Go, the app you'll run your project in. Open on YouTube. Auto-generated captions only; everything in it is covered in the notes below.

In HOS 1 you split the app into a frontend and a backend. Here's the payoff: adding a phone app doesn't touch the backend's AI logic at all. The Expo (React Native) chat screen calls the same POST /chat endpoint Streamlit did, with the same JSON in and the same JSON out. The backend can't tell which client is asking, and it doesn't need to.

Streamlit pagein the browser
⇄
Backend 🔑FastAPI POST /chat, unchanged. Still the only place the API key lives.
⇄
Expo appon your phone, through Expo Go

React Native lets you write a phone app in JavaScript and React; Expo is the toolkit around it that handles building and running. During development you don't install anything through an app store: the free Expo Go app on your phone loads your project when you scan a QR code.

Three practical details decide whether the phone can reach your code at all:

  1. Tunnel mode. Your phone and your Codespace aren't on the same network, so start Expo with npx expo start --tunnel. The default LAN mode just appears to hang.
  2. A public backend port. The phone calls your backend over the internet, so the Codespace's backend port must be set to public, and the app must use that public URL, not localhost.
  3. CORS. When the Expo app runs in a web browser, the browser blocks calls to a different domain unless the backend allows them, which is what the CORSMiddleware lines in the guide do.

On iOS, Expo Go also needs you signed in to the same Expo account in the terminal and in the app.

Worked example

A student's app loads, but every message shows "Network request failed." The chat screen calls http://localhost:8000/chat. On a laptop that's the backend; on a phone, localhost means the phone itself, where nothing is listening. Switching to the Codespace's public forwarded URL fixes it. No backend code changed, because nothing in the backend was wrong.

⚠ Common mistakes

  • Using localhost from the phone. It points at the phone. Use the public URL.
  • Leaving the backend port private. The phone gets an error or a sign-in page instead of JSON.
  • Putting the Gemini key in the mobile app "just for testing." Anything shipped in an app can be extracted from it. The key stays in the backend, exactly as in HOS 1.
Quick check

Your Streamlit frontend and your phone app both call /chat. Where does the Gemini API key live now, and did anything about that need to change?

Part 2 — Push notifications: a chain that fails silently ≈ 5 min

HOS 3 moved document ingestion into a background job, which means the user is no longer waiting when it finishes. Polling GET /jobs/{id} works while the app is open; a push notification closes the loop even when it isn't: "your document is ready," delivered to a closed app.

Your backend can't reach a phone directly. Phones only accept pushes from their platform's push service (Apple's for iPhones, Google's for Android). Expo's push service sits in front of both, so your backend sends one kind of request and Expo forwards it. The address is an Expo push token, a string that identifies one app on one device.

It only works if every link holds:

  1. The app asks for, and gets, notification permission.
  2. The phone gets an Expo push token, an address for this device. (This needs a free EAS project ID: run npx eas init once.)
  3. The app sends the token to the backend: POST /register-device.
  4. The upload includes the device_id, so the job knows whom to notify.
  5. When the job finishes, the backend sends a message to Expo's push service, addressed to that token.
  6. Expo hands it to Apple's or Google's service, which delivers it to the phone.

Step 5 is a single HTTP request. Its response is where silent failures hide:

resp = requests.post(
    "https://exp.host/--/api/v2/push/send",
    json={"to": push_token, "title": "Document ready", "body": "returns.pdf is searchable now"},
)
# resp.status_code is 200 even when delivery failed.
# The real outcome is in the body:
#   {"data": {"status": "ok", ...}}
#   {"data": {"status": "error", "details": {"error": "DeviceNotRegistered"}}}

Break any link and nothing errors: the notification just never comes. Expo's push service returns 200 OK even for a stale or invalid token, so a backend that only checks the status code reports success for a message nobody will see. And one platform limit: Expo Go on Android no longer supports push (SDK 53 and later). Chat works on Android, but to prove push, use an iPhone or a free development build.

Worked example

Push worked yesterday and doesn't today. The job finished (its status is finished), the backend log shows the request to Expo, and the response was 200. Reading the body shows "DeviceNotRegistered": the student reinstalled Expo Go, which issued a new token, and the backend still has the old one. Re-registering the device fixes it. The lesson is to walk the chain in order and read each link's evidence rather than guessing.

⚠ Common mistakes

  • Trusting the 200. Always read the response body from Expo's push service.
  • Testing push in Expo Go on Android. It can't receive pushes any more; use an iPhone or a development build.
  • Forgetting the device_id on upload. The job finishes fine but has no one to notify.
Quick check

The job's status is finished but no notification arrived. List the links you'd check, in order, and the evidence you'd look for at each one.

Part 3 — Observability: traces, spans, and scores ≈ 5 min

Optional video10:09 · Langfuse

A tour of the dashboard you'll use, from the people who make it. Watch the tracing and scores sections; prompt management and datasets are beyond this module. Open on YouTube. Auto-generated captions only; everything in it is covered in the notes below.

Logs tell you that something happened. A trace tells you the whole story of one request: a tree of spans, one per step, each with its own timing, inputs and outputs. In this HOS, Langfuse's @observe() decorator on run_agent() and retrieve() produces a trace where retrieval and generation are separate, nested spans:

@observe()
def retrieve(query, k=5):      # becomes a child span: its own timing, input and output
    ...

@observe()
def run_agent(message):        # becomes the top-level span for the whole request
    chunks = retrieve(message) # called inside, so it nests under run_agent
    ...

You add one line per function and get the nesting for free, because Langfuse records which observed function called which.

run_agent
1.9 s
  retrieve
0.32 s
  generation
1.47 s

Illustrative. Real traces also show tokens, inputs and outputs per span.

Read a waterfall like this from the top. The parent bar is the whole request. Each child bar shows where inside it time went: here, three quarters of the request is the model generating the answer, so making retrieval faster would barely help.

Timing is only half of it. AI output is probabilistic, so "did the request succeed?" isn't enough; you also need "was the answer any good?" That's what a score is: a number attached to a trace. This HOS uses faithfulness: is the answer supported by the retrieved context, or did the model add things? You'll write your own score_faithfulness(answer, context) in Understand & Refine. A simple version checks what share of the answer's sentences have support in the retrieved chunks: 3 of 3 supported scores 1.0, 2 of 3 scores 0.67.

Scores accumulate across runs, so you can see whether quality is trending up or down after a change. That's the "appropriate observability tools and metrics for assessing probabilistic outputs" in Outcome O4: one score tells you little; a trend tells you whether your last change helped.

Worked example

A user says the assistant told them Northwind offers gift wrapping. You open that request's trace. The retrieve span returned two chunks about packaging and shipping, nothing about gift wrap. The generation span's output stretched them into a policy. Faithfulness scored 0.67. Diagnosis in two minutes: a retrieval and grounding problem (HOS 2), not a model problem.

⚠ Common mistakes

  • Expecting traces without keys. With no Langfuse keys set, the app still works and simply sends nothing. That's by design, not a bug.
  • Decorating only the top function. You get one bar for the whole request and can't see where time went. Decorate the steps too.
  • Treating one score as a verdict. A heuristic score is noisy. Look at the trend, and read the trace behind any surprising number.
Quick check

A request takes 6 seconds. The trace shows retrieve at 0.3 s and generation at 5.5 s. Where would you look first to speed it up, and what would you not bother optimising?

New words this week (4)
Push notification & push token
A message delivered to a device even when the app is closed, addressed with a token unique to that device.
Expo & Expo Go
A framework for building iOS/Android apps in JavaScript, and a free phone app that runs your project without app-store builds.
Trace & span
The full record of one request, and one timed step inside it. Spans nest: retrieval sits inside the agent run.

A number attached to a trace to measure quality; faithfulness measures whether the answer is supported by the retrieved context.

    Concept Debate

    Discussion board · 3 stages
    This week's question

    Should a production AI app trace and score every request, or only a sample of them?

    You'll argue the side your debate group is assigned, then argue the other one, then drop advocacy and synthesize.

    Your side this HOS

    Sides rotate each HOS. In HOS 4, Debate Group 1 argues Side B and Debate Group 2 argues Side A. Find your group under Communication → Groups in Brightspace. Not in a group? Before posting Stage 1, count the posts on each side and join the side with fewer; if they're tied, take Side A. How sides are assigned →

    Side A — Trace and score everythingGroup 2 this HOS

    Every request gets a full trace and a faithfulness score.

    • The one wrong answer a user complains about is exactly the one a 10% sample will have missed.
    • AI failures are rare and probabilistic — you need volume to see them.
    • Free tiers are generous at course scale; cost only matters later.

    Side B — Sample a fraction of requestsGroup 1 this HOS

    Trace and score a representative sample, plus every request that errors.

    • Every trace stores user questions and retrieved documents — more data kept means more privacy risk.
    • Scoring every answer (especially with another model) can cost as much as answering it.
    • Trends need a good sample, not a census.

      Integration Concept Debate — connecting all 4 HOS

      Same 3-stage format
      The question

      Under a Term Project deadline, which of the 4 HOS is safest to cut a corner on — and which one can't be shortchanged?

      Your side

      For the Integration debate, Debate Group 1 argues Side A and Debate Group 2 argues Side B. In Stage 3, your synthesis must name both the safest corner to cut and the one you'd never shortchange.

      Side A — Observability (HOS 4) is the safest corner to cutGroup 1

      • Users never see traces; a demo works without them.
      • Tracing can be added after launch without changing behavior.
      • Without guardrails (HOS 3) or grounding (HOS 2), users get wrong answers today.

      Side B — Never cut observability; cut async (HOS 3's queue) insteadGroup 2

      • Without traces, every bug in demo week becomes guesswork.
      • At project scale, uploads are small — inline ingestion is slow but tolerable.
      • You can't show a grader that retrieval works without evidence.
