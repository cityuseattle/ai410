How to use this page

Course rules this page follows: everything below runs in a GitHub Codespace and needs no credit card (Gemini, Upstash, Langfuse, and Expo all have free tiers).

What "starter code" means in this course

Each HOS has a starter-code folder on GitHub, and each folder is a complete snapshot of the app as it stands when that HOS begins. HOS 1's folder is nearly empty on purpose — you scaffold the app yourself with an AI assistant. From HOS 2 on, the folder is a reference version of your previous HOS's finished result, carried forward, plus the blank spot where this HOS's new piece goes — so everyone starts from the same working code even if their own AI-scaffolded version differs. That means your first job in each HOS is reading working code you did not type out yourself. This page explains that code, one HOS at a time.

Don't read ahead. The section for HOS 3 explains the retrieval code you build in HOS 2; the section for HOS 4 explains the guardrail and queue code you build in HOS 3. Each HOS grades you on explaining that code in your own words (the Analyze stage), so read a section only when you're starting that HOS — at which point it describes code you've already written and understood.

1️⃣

Starting HOS 1

Almost empty on purpose

The folder contains exactly two useful things, and no application code at all:

.devcontainer/devcontainer.json — your Codespace, pre-configured

When you open the folder as a Codespace, GitHub reads this file and builds a container for you: a Python 3.12 image, then a postCreateCommand that copies .env.example to .env (the -n flag means it never overwrites a .env you've already filled in). It also forwards ports 8000 and 8501, which your backend and frontend will use once you build them. From HOS 2 on, this same file also installs the requirements for you.

Why it matters: a brand-new container has nothing else installed, so a stray global package on your own laptop can't silently shadow the project's real dependencies — the most common setup bug in this course.

Watch out: in HOS 1 there are no requirements files yet, so nothing is installed for you. You (or your AI assistant) create requirements.txt files and run pip install -r yourself. That's expected.
backend/.env.example — where your API key goes 
GEMINI_API_KEY=your-key-here

A template, safe to commit. You put your real Gemini key (free, no credit card, from aistudio.google.com/apikey) in backend/.env, which is git-ignored so it never leaves your Codespace. Treat the key like a password — see the Account & Service Setup Guide.

2️⃣

Starting HOS 2

Reference HOS 1 result, carried forward

You're handed a working chat app with an agent that can call tools. Nothing here needs to change in HOS 2 — but you need to understand it, because everything you add in HOS 2 plugs into it.

  • backend/main.py, agent.py, tools.py, requirements.txt, .env.example
  • frontend/app.py, requirements.txt
  • backend/sample_docs/ — five markdown documents for a fictional outdoor-gear company (Northwind Outfitters): backpacks, tents, return policy, shipping, warranty. This is the raw material for HOS 2's retrieval work.

How one chat message travels

The green box is the heart of the app. The loop between agent.py and Gemini repeats until Gemini replies with plain text instead of asking for a tool.

backend/agent.py — the agentic loop

One function, run_agent(user_message), does everything:

  1. Sends the user's message to Gemini along with the list of tools it's allowed to use (client.interactions.create(..., tools=TOOLS)).
  2. Looks through the reply's steps for any of type "function_call". None? The model has a plain-text answer — return interaction.output_text and stop.
  3. Some? For each one, look up the Python function by name in TOOL_FUNCTIONS, run it locally with the model's arguments, and wrap the output as a "function_result".
  4. Send those results back with previous_interaction_id so Gemini continues the same conversation, and go around again.
for _ in range(MAX_TURNS):
    function_calls = [s for s in interaction.steps if s.type == "function_call"]
    if not function_calls:
        return interaction.output_text      # done: plain answer
    ...                                      # run each tool, build results
    interaction = client.interactions.create(
        model=MODEL, input=results, tools=TOOLS,
        previous_interaction_id=interaction.id,
    )
Two safety nets to notice: MAX_TURNS = 5 is a hard ceiling so a model that keeps asking for tools can't loop forever, and an unknown tool name returns an error string to the model rather than crashing the request — so the model gets a chance to recover.

The model never runs your code. It only asks; your code decides whether and how to run it.

backend/tools.py — what the model can ask for

Every tool is two halves that share a name:

  • A schema in the TOOLS list — the name, a description, and a JSON-schema for its parameters. This is all Gemini ever sees. The description is what it reads to decide when to call the tool, so a vague description makes it over- or under-eager.
  • A Python function registered in TOOL_FUNCTIONS under the same name. This is what actually runs.

Two tools ship: calculate (arithmetic) and word_count (a single string argument, deliberately a different shape so you can't adapt one from the other without understanding the registration pattern).

Notice how _calculate is written. It does not call Python's eval() on the model's text. It parses the expression into a syntax tree with ast and only evaluates a whitelist of operators (+ − × ÷ ** and unary minus). eval() on model output would let a prompt trick the agent into running arbitrary code — a real vulnerability, not a hypothetical one.

Both functions accept **kwargs, which quietly absorbs any extra argument the model invents instead of crashing with a TypeError.

backend/main.py — the HTTP front door

A small FastAPI app with two endpoints:

  • POST /chat — takes {"message": "..."}, calls run_agent, returns {"reply": "..."}.
  • GET /health — returns {"status": "ok"}; the quickest way to check the server is up.

The ChatRequest/ChatResponse classes are Pydantic models: FastAPI uses them to validate incoming JSON (a request missing message is rejected with a 422 before your code runs) and to shape the response. There's no CORS setup on purpose — the Streamlit frontend calls this server from Python, not from browser JavaScript, so the browser's cross-origin rules never apply.

Interactive docs for free: with the server running, open /docs to try endpoints from the browser.

frontend/app.py — the chat UI

A Streamlit app, run as its own Python process. It keeps the conversation in st.session_state.messages (Streamlit reruns the whole script on every interaction, so anything not stored there would vanish), draws each past message, and on new input POSTs to http://127.0.0.1:8000/chat with a 30-second timeout. If the backend is down or slow, the except shows a readable error in the chat instead of a stack trace.

Watch out: the backend and frontend are two separate processes in two terminals. 127.0.0.1 works in a Codespace because both run inside the same container.
requirements.txt · .env.example · devcontainer.json — setup files
  • backend/requirements.txt pins exact versions: fastapi, uvicorn, google-genai, python-dotenv, pydantic. Pinning means everyone in the class gets the same behavior.
  • frontend/requirements.txt: streamlit and requests.
  • devcontainer.json installs both requirement files and forwards port 8000 (the API) and 8501 (Streamlit, which opens as a preview automatically).

A few header comments in this code still name the HOS it was first written in (for example, main.py may say "HOS 1"). The code is what counts.

3️⃣

Starting HOS 3

Reference HOS 2 result, carried forward

Everything from HOS 2, plus retrieval. The agent can now answer questions about the Northwind documents instead of guessing. New this time: backend/ingest.py, backend/retrieval.py, a changed agent.py, and chromadb in requirements.txt.

Two phases: prepare once, then look up per question

Both phases use the same embedding model, which is why a few settings in ingest.py and retrieval.py have to match exactly.

backend/ingest.py — prepare the documents (run once)

For every .md file in sample_docs/:

  1. Chunk it with chunk_text: split into words, cut into chunks of 400 words, each starting 50 words before the previous one ended (overlap=50) so an idea that straddles a cut still appears whole in at least one chunk.
  2. Embed all the chunks in one call to gemini-embedding-001, which turns each chunk into a list of 1,024 numbers (output_dimensionality=1024) that capture its meaning.
  3. Store them in a local Chroma collection named documents (saved in backend/chroma_db/), with an id like return-policy.md-0 and the source filename as metadata.

It's a plain script (python ingest.py), not part of the web app — it prepares the database the app later reads.

Watch out: chroma_db/ is git-ignored, so each Codespace builds its own copy. New Codespace or new document means run ingest.py again.
backend/retrieval.py — find the relevant chunks per question

retrieve(query, k=5) embeds the incoming question the same way, then asks Chroma for the k stored chunks whose vectors are closest to the question's vector, and returns their text. "Closest" here means "most similar in meaning", which is why a question like "can I send back a tent?" can match a return-policy chunk that never uses those exact words.

Note the constants at the top: EMBED_MODEL, EMBED_DIM, and CHROMA_PATH are repeated in ingest.py. They must match — vectors of different sizes can't be compared.

It opens the Chroma database on each call. That's fine at this scale and keeps the function self-contained.

backend/agent.py — what changed — retrieved context joins the prompt

At the top of run_agent, the new code calls retrieve(user_message, k=5), joins the chunks into one block, and puts it in a system_instruction that's passed on every Gemini call in the loop. The instruction tells the model to answer Northwind questions from that context, to say it doesn't know rather than guess, and — importantly — that this restriction does not apply to its tools, so calculate still works on questions the documents don't cover.

Think about it: that last sentence exists because of a real bug pattern — tell a model "only use this context" and it may refuse to use tools at all. Prompts are part of your program's logic.

The rest of the loop is unchanged from HOS 2.

4️⃣

Starting HOS 4

Reference HOS 3 result, carried forward

Everything from HOS 3, plus two more layers: guardrails around tool arguments, and async document ingestion through a background queue. New files: guardrails.py, jobs.py, queue_setup.py, worker.py. Changed: main.py and agent.py. The mobile/ folder is empty — that's yours to build this HOS.

backend/guardrails.py — validate what the model sends, retry if it's wrong

Model output is non-deterministic: a tool call's arguments can arrive missing a field or the wrong type. call_with_guardrail(fn, schema, ...) wraps that risk:

  1. Call fn and validate what it returned against a Pydantic schema.
  2. On a ValidationError, log it and try again, up to max_retries (default 2) times.
  3. Return the validated object on success — or, if every attempt fails, a plain dict with an "error" key. It never raises, so the caller can always handle failure calmly.

Two schemas live here: CalculateArgs (requires a string expression) and WordCountArgs, which adds a validator rejecting blank text — a case the tool itself would happily "count" as zero words rather than flag as a bad call.

Look closer: in agent.py the guardrail wraps lambda: call.arguments — a function that returns the same arguments on every attempt. So what does a retry actually change? Consider what value the guardrail provides as written, and what a retry would need in order to help (hint: the correction_hint parameter).
backend/agent.py — what changed — guardrails around both tools

Inside the loop, before running a tool, calculate and word_count calls now go through call_with_guardrail. If validation succeeds, the tool runs with the validated arguments (validated.model_dump()); if not, the {"error": ...} dict goes back to the model as the tool's result, giving it a chance to correct itself instead of crashing the request.

Why ingestion moved to a queue

Embedding a big document can take a while. Instead of making the request wait, main.py hands the work to a queue and answers immediately with a job id; a separate process does the slow part.

backend/main.py — what changed — two new endpoints
  • POST /documents — takes {"doc_path": "..."} (a file already on the server, for this exercise), calls queue.enqueue(ingest_document_job, doc_path), and returns {"job_id": ...} right away.
  • GET /jobs/{job_id} — looks the job up in Redis (Job.fetch) and returns its status (queued, started, finished, failed) and result.

The chat path is untouched.

backend/queue_setup.py — connect to Redis

Two lines that matter: Redis.from_url(os.environ["REDIS_URL"]) connects using the connection string from your free Upstash database, and Queue("ai410-ingestion", ...) creates a named queue on it. Both main.py (to add jobs) and worker.py (to take them) import the same objects from here.

Watch out: it reads REDIS_URL with os.environ[...], so a missing value crashes on import with a KeyError rather than failing later. The value must start with rediss:// (two s's) — see the Redis section of the setup guide.
backend/jobs.py — the work the worker does

ingest_document_job(doc_path) reads one document, chunks it, embeds it, and adds it to the same Chroma collection — the same recipe as ingest.py, returning {"chunks_inserted": n}, which RQ saves as the job's result.

Why is the code duplicated instead of imported? The worker runs as a separate process with its own memory, so this file is deliberately self-contained — including its own load_dotenv(), because the environment variables loaded by main.py don't exist in the worker's process.

backend/worker.py — the process that does the queued jobs

Create a Worker on the queue and call .work(): it waits for jobs and runs each one. Nothing starts it automatically — you run python worker.py in its own terminal alongside uvicorn.

The #1 async bug: a job stuck on queued forever almost always means the worker isn't running.
Config that changed — .env.example, requirements, devcontainer
  • .env.example now also lists REDIS_URL (Upstash) and three Langfuse values: LANGFUSE_PUBLIC_KEY, LANGFUSE_SECRET_KEY, LANGFUSE_HOST. Langfuse is what you'll wire up for tracing this HOS — free tier, no credit card.
  • requirements.txt adds redis and rq (the queue library).
  • devcontainer.json adds Node 20 (for the Expo mobile app) and forwards port 8081, the Expo dev server.

Running it in a Codespace

Open the HOS folder as a Codespace (Code → Codespaces → Create codespace on main). The devcontainer installs dependencies and creates backend/.env for you. Add your real keys to that file, then use one terminal per process:

# Terminal 1 — the API
cd backend
uvicorn main:app --reload

# Terminal 2 — the chat UI
cd frontend
streamlit run app.py

# HOS 2 onward, once (and after adding a document)
cd backend
python ingest.py

# HOS 4 only — Terminal 3, the queue worker
cd backend
python worker.py

No virtual environment needed — the Codespace is already an isolated container. Check the API is alive at /health; try endpoints at /docs. Stop your Codespace when you're done — free hours are limited.

How to read code you didn't write

  1. Start at the entry point. For this app, that's main.py — every request enters here.
  2. Follow one request end to end. Pick a single chat message and trace it file by file, like the diagrams above, before you read anything else.
  3. Run it before you change it. Send a message, ask a question the documents cover, ask one they don't. Watching real behavior beats guessing.
  4. Break it on purpose. Stop the worker, blank the API key, ask for something the tool can't do. Knowing how it fails is how you know you understand it.

This is the same habit the Evaluate and Analyze stages of every HOS are training.
