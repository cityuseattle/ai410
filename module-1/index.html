What's the HOS?

HOS 1 (Hands-On Skill) is this module's main build and 10% of your course grade. It has four stages across the two weeks: Create / Scaffold and Evaluate in Week 1, then Analyze and Understand & Refine in Week 2. All four go in one GitHub repo, and you submit that repo's link once, in Brightspace, at the end of Week 2. The Muddiest Point, Concept Debate, Application Challenge and Knowledge Check are graded separately.

Most people meet a large language model through a chat box, and it's easy to think the chat box is the model. It isn't. Behind every AI product there are at least three separate pieces — a frontend the user sees, a backend that holds secrets and makes decisions, and the LLM itself, which only ever turns text into more text. This first HOS is about seeing those pieces clearly, and then about the one idea that turns a chat app into an agent: letting the model ask your code to run a real function and wait for the answer.

You'll spend Week 1 getting a working app running quickly with an AI coding assistant and then judging it on purpose. Week 2 is the harder half: explaining exactly how the loop works, extending it by hand, and applying the same judgment to a business you've never built for.

Anchoring analogy

Think of the LLM as a very well-read consultant on a phone line. They can reason, explain, and draft — but they can't touch anything. A tool is you, on the other end, offering "I can look that up / run that calculation for you." The agentic loop is the conversation where the consultant says "please run calculate('342*87') and tell me what you get," waits for your answer, and only then replies to the customer. The consultant never sees your filing cabinet; they only ever see what you read back to them.

Learning objectives

By the end of the two weeks you will be able to:

  1. Identify the frontend, backend, and LLM in a full-stack AI app, and explain why the API key belongs only in the backend. O1
  2. Describe what an LLM actually produces — tokens predicted from a context window — and why the same input can give different outputs. O1
  3. Distinguish prompt engineering (wording the request) from context engineering (deciding what information the model sees). O1
  4. Trace the agentic loop step by step: model → function call → backend executes → result returned → final answer. O1
  5. Judge which functions a model should be allowed to call on its own, and which need a human in the loop. O1

Part 1 — Anatomy of a full-stack AI app ≈ 5 min

Optional video1:15 · Codecademy

A quick picture of the two halves of every app you'll build. Watch for what each half is responsible for, then read on for the part the video skips: why the API key has to live in the backend. Open on YouTube. Auto-generated captions only; everything in it is covered in the notes below.

Every app you build this term has the same three-piece shape. The frontend (a Streamlit page now, an Expo mobile app in HOS 4) collects the user's message and shows the reply. The backend (a FastAPI server) receives that message over HTTP, adds anything the model needs, calls the LLM, and runs any tools. The LLM (Google's Gemini, via the free API) receives text and returns text — or, as you'll see in Part 3, a structured request to run a function.

FrontendStreamlit chat page. Runs on the user's machine / browser. Anyone can inspect it.
⇄
Backend 🔑FastAPI POST /chat. Holds GEMINI_API_KEY in .env. Runs tools.
⇄
LLMGemini API. Sees only what the backend sends it.
Worked example

A classmate ships a quick demo that calls Gemini directly from the frontend, with the API key pasted into the JavaScript. It works — and within an hour of posting the link, anyone who opens the browser's developer tools can copy the key and spend its quota. Moving the call behind a backend endpoint doesn't make the app smarter; it makes the secret unreachable. That's the first reason the backend exists. The second is that tools (Part 3) have to run somewhere trustworthy too.

The two halves talk over HTTP. The frontend sends a request (POST /chat with a small JSON body such as {"message": "What's 342 times 87?"}) and the backend answers with JSON ({"reply": "342 × 87 = 29,754."}). That request and response are the contract between the halves. As long as it stays the same, you can replace either side: HOS 4 adds a phone app without touching the backend's AI code at all.

⚠ Common mistakes

  • Putting the API key anywhere the user's device can see it: frontend code, a mobile app, or a public repo. It belongs in backend/.env, which is git-ignored.
  • Committing .env. If a key ever lands in a commit, treat it as leaked: delete it in Google AI Studio and make a new one.
  • Calling the model from the frontend "just for now." Shortcuts like this tend to ship. Start with the backend in the middle.
Quick check

Name two things the backend does that the frontend must never do, and one reason for each.

Part 2 — What an LLM actually does ≈ 15 min

Watch first7:58 · 3Blue1Brown

Watch for two ideas this lesson builds on: the model predicts the next word piece from probabilities, and it samples, so the same input can give different answers. Open on YouTube (human captions).

Go deeper (optional): IBM Technology, Context Engineering vs. Prompt Engineering (7:52). It explains the difference in the table below, then goes on to retrieval and agents, which you'll meet in Module 2 and later courses.

An LLM reads a sequence of tokens (word pieces) and predicts the next one, over and over, until it decides to stop. Everything it "knows" about your conversation is whatever fits in its context window for that single request — the system instruction, the chat history your backend chose to resend, any retrieved documents, and the user's latest message. It doesn't remember the last request unless you send it again.

Because each next token is sampled from a probability distribution, the same input can produce different outputs. That nondeterminism is a feature for writing and a hazard for software — it's why HOS 3 adds guardrails, and why "it worked once" is never a complete Evaluate.

Question it answersHow should I word the request?What information should the model see at all?
Where it livesThe instruction textThe backend code that assembles each request
Example"Answer in two sentences, cite the policy."Resend only the last 6 turns; attach the 3 most relevant policy chunks; list the tools available.

Worked example

A student types "I'm Dana," then "What's my name?" The Streamlit page shows both messages, so it looks like a conversation with memory. The model answers "I don't know your name." In the HOS 1 build, the frontend keeps the chat on screen, but each POST /chat sends only the latest message, and the backend starts a fresh request to Gemini every time. What the user sees and what the model sees are different things. If you want the model to remember, your backend has to send the earlier turns.

⚠ Common mistakes

  • Believing the model remembers you. It only sees what's in this request. History is your backend's job.
  • Testing once. Sampling means one good answer proves little. Run important checks several times.
  • Sending ever-longer history. Every resent turn costs tokens and eventually hits the context window. Real apps trim or summarise.
Quick check

The Streamlit page keeps a list of every message, but the backend receives only the latest one. Does the model remember earlier turns? Decide, then confirm by trying it in Week 1's build.

Part 3 — The agentic loop & tool calling ≈ 10 min

Watch first2:55 · Google Cloud Tech

The same Gemini API you'll use in the build. Watch for the moment the model asks for a function instead of answering, and who actually runs it. The model names in the video may be older; use gemini-3.8-flash, as in the hands-on guide. Open on YouTube (human captions).

Go deeper (optional): IBM Technology, What is Tool Calling? (4:56). The same idea without tying it to one vendor; its second half covers a variation that's beyond this module.

A plain chat app is one round trip: message in, text out. An agent adds a loop. Your backend tells the model which functions exist (a name, a description, and a parameter schema). When the model decides a function would help, it doesn't reply with text — it replies with a function call: a name and arguments. Your backend runs the real function, sends the result back, and asks again. The loop ends when the model replies with plain text.

  1. User types "What's 342 times 87?"; the frontend POSTs it to /chat.
  2. Backend sends the message + the calculate tool declaration to Gemini.
  3. Gemini replies with function_call: calculate(expression="342*87") — no text yet.
  4. Backend runs the real Python function → 29754.
  5. Backend sends the function_response back to Gemini, along with the history so far. (This is the "loop" — it can repeat.)
  6. Gemini replies with text: "342 × 87 = 29,754." Backend returns it to the frontend.
# the shape of a tool declaration (simplified)
calculate_tool = {
    "name": "calculate",
    "description": "Evaluate a basic arithmetic expression. Use for any math.",
    "parameters": {
        "type": "object",
        "properties": {"expression": {"type": "string", "description": "e.g. '342*87'"}},
        "required": ["expression"],
    },
}

Notice what the model never does: it never runs the function. It only asks. That's the property that makes tool calling safe to reason about — and it's why deciding which functions to expose is an engineering judgment, not a detail (you'll practice that in the Application Challenge).

⚠ Common mistakes

  • A vague tool description. The description is the only thing the model reads to decide when to call a tool. "Does math" gets ignored; "Evaluate a basic arithmetic expression. Use for any math." gets used.
  • Forgetting to send the result back. If the backend runs the tool but never returns a function_response, the model never gets to answer.
  • No limit on the loop. A model that keeps asking for tools can loop forever. Cap the number of turns.
  • Letting a tool crash the request. Wrap the tool in try/except and return the error as data, so the model can explain it.
Quick check

A user asks "What's 2 + 2, and what's 10 times that?" How many times might the loop go round, and what does the backend send Gemini on each pass?

▶ Rehearse before the build: Open the Agentic Loop Simulator and step through "What's 342 times 87?", then "Tell me a joke", then "Calculate 12 / (3 -". Watch where each one exits the loop.

New words this week (4)
Frontend / backend
What the user sees vs. the server that holds your API key and runs tools.
Token & context window
The word pieces a model reads and writes, and the maximum amount of them it can consider in one request.
Agentic loop
The cycle of model → function call → your code runs it → result back to the model, repeated until the model answers in text.
Tool / function declaration
The name, description, and parameter schema you give the model so it knows a function exists and how to ask for it.

    Concept Debate

    Discussion board · 3 stages
    This week's question

    When a request might need a tool, who should decide — the model, or deterministic backend code?

    You'll argue a side you're assigned, then argue the other one, then drop advocacy and synthesize. Nobody gets to post "I agree" — by Stage 3 everyone has argued both sides.

    How your side is assigned

    Before the first debate you join Debate Group 1 or Debate Group 2, either assigned by your instructor or chosen yourself, as long as the two groups stay close to even. You stay in that group all term; find yours under Communication → Groups. The sides rotate each HOS, so nobody argues the same kind of position all term:

    Not in a group? (for example, you added the course late) Before posting Stage 1, count the posts on each side and join the side with fewer; if they're tied, take Side A.

    Side A — Let the model decideGroup 1 this HOS

    Declare the tools and let the LLM choose when to call them.

    • Handles phrasing no rule anticipated ("what's a 15% tip on $48?").
    • Adding a tool is one declaration, not a new routing rule.
    • This is how the Gemini function-calling API is designed to work.

    Side B — Backend code decidesGroup 2 this HOS

    Use rules (regex, keywords, a classifier) to decide, and only ask the model to phrase the answer.

    • Deterministic: the same input always takes the same path — testable.
    • The model can't call a tool it was never routed to.
    • Cheaper: fewer model round trips per request.
