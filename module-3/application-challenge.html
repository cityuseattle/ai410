Application Challenge 3: Pacific Bean Coffee Refund Guardrail

Take the guardrail and background-job skills from HOS 3 to a tool that moves money: validate every call the model makes to a refund tool, route good calls either straight through or to a human review queue, and decide what the bot may refund on its own.

📏

Ground rules

Everything here runs in GitHub Codespaces on free tiers, with no credit card. Everything runs offline with no API key or Redis instance.
🏢

The scenario

Pacific Bean Coffee Co. (fictional) sells beans and equipment online, to home customers and to cafes. Its support chatbot can call one tool: issue_refund(order_id, amount, reason, note?). In testing, the model filled in those arguments wrong in a dozen ways. They're all in recorded_calls.json: an amount of "twenty dollars", a negative amount, an order number without its prefix, a made-up "approved": true field, someone else's order.

  • The app knows who is logged in. Like AC 1, the customer ID comes from the app, never from the model.
  • The review queue stands in for HOS 3's Redis queue. enqueue returns a job ID immediately, and a person at Pacific Bean works through the jobs later.
📐

The spec

Every requirement below is checked by a provided test in tests/test_refunds.py. Your code goes in refunds.py.

LayerMust do
Schema (RefundArgs, Pydantic)Order ID is PB- plus 4 digits; amount is a number above 0 with at most 2 decimals; reason is one of four; note is optional, at most 200 characters; any other field is rejected.
Lookup (the order data)Reject an order that doesn't exist or isn't this customer's, with the same message for both. Reject orders older than 30 days. Reject an amount above what's left to refund, and say what's left.
RoutingOver $500 is never applied: it goes to the review queue. Otherwise your rules decide. A small "damaged" refund on a recent order goes straight through.
Every errorReturns {"error": ...} naming every bad field, so the model can retry (the HOS 3 pattern), and changes nothing.

The open decision: what the bot may refund on its own

The owner: "Handle refunds so I don't have to. But never let the bot refund more than $500 on its own." Everything at or under $500 is your call.

Set AUTO_REFUND_LIMIT, and add any other rule that sends a refund to a person: a reason, a repeat refund on the same order, an account type. Prove your rules with your own tests and defend them in DECISIONS.md.

💡

Where each check belongs

In your memo, take the bad calls in recorded_calls.json and say which layer stops each one in your code (schema, lookup, or person), and why an earlier layer can't. Then name one call that could pass every check you wrote and still be a refund the owner wouldn't want.

🪜

Steps & what to submit

1Open it and run the tests

Open your own AC 3 repo (accept the invite linked in Brightspace under AC03) in GitHub Codespaces. It installs everything for you. Then run:

pytest

Almost everything fails. That's your to-do list.

2Build the schema

Write RefundArgs until the schema tests pass. You may use an AI assistant; read what it writes, because you'll defend it.

3Build the lookup and routing

Write issue_refund: validate, check the order, then route. Make sure an error or a queued refund never changes the order.

4Make the routing call

Set AUTO_REFUND_LIMIT and any other rules. Write at least two tests in tests/test_my_rules.py: one refund that goes straight through and one that's queued, plus the case closest to your limit.

5Replay the recorded calls

Run every recorded tool call through your code:

python run_cases.py

Paste the output into REPORT.md and fill in DECISIONS.md.

Submit (via Brightspace)
  • refunds.py and tests/test_my_rules.py
  • The output of pytest, pasted as text (all tests passing, including yours)
  • REPORT.md
  • DECISIONS.md

How this differs from HOS 3's Understand & Refine: there you guarded your own second tool, by hand. Here the tool moves real money, the bad calls are someone else's, AI help is allowed, and half the grade (Analysis and Evaluation) is for the calls you make.

🧯

Common snags

  • "twenty dollars" or 12.833 gets through. Pydantic turns numeric strings into numbers on its own, but not words. Use Field(gt=0) for the sign and a field_validator for the decimals.
  • "approved": true gets through. Pydantic ignores unknown fields by default. Set model_config = ConfigDict(extra="forbid").
  • The error only names one field. Catch the ValidationError and loop over e.errors(), so the model can fix every field in one retry.
  • A test says an error changed an order. Do every check before you add to refunded, not after.
