What's the HOS?

HOS 3 (Hands-On Skill) is this module's main build and 10% of your course grade. It has four stages across the two weeks: Create / Scaffold and Evaluate in Week 5, then Analyze and Understand & Refine in Week 6. All four go in one GitHub repo, and you submit that repo's link once, in Brightspace, at the end of Week 6. The Muddiest Point, Concept Debate, Application Challenge and Knowledge Check are graded separately.

Your HOS 2 app works — most of the time. That's the problem this HOS is about. A model that returns valid tool arguments 95% of the time will, across a few hundred requests a day, hand your code garbage several times a day. And a document upload that takes twenty seconds to chunk and embed will, if it runs inside the web request, freeze the app for everyone while it runs. Neither shows up in a quick demo. Both show up the first week real people use it.

This HOS adds the two reliability layers every production agent needs: a guardrail that checks model output before your code trusts it, and a queue with a background worker that moves slow work off the request path. Week 5 builds and tests both. Week 6 explains why they're designed the way they are, extends the guardrail by hand, and ends with a quick check-in on your Term Project.

Anchoring analogy

A busy restaurant has two rules. First, the kitchen reads back every order ticket before cooking — "no onions, extra sauce?" — because a waiter who's right 95% of the time still ruins a dish every night. That's the guardrail. Second, the waiter doesn't stand at the counter while a 40-minute brisket cooks; they hand the kitchen a ticket, take a number, and go serve other tables. That's the queue: the ticket number is your job_id, and the cook working in the back is your worker process.

Learning objectives

By the end of the two weeks you will be able to:

  1. Explain why nondeterministic model output must be validated before code acts on it. O3
  2. Implement a validate-and-retry guardrail that feeds the validation error back into the retry, and fails to data instead of crashing. O3
  3. Distinguish structural validation (a schema can check it) from semantic validation (it needs a lookup or a human). O3
  4. Analyze where an agent-driven app bottlenecks, and move long-running work to a queue and worker. O3
  5. Diagnose the common failures of a queue-based design, including a worker that isn't running. O3

Part 1 — Nondeterminism reaches your code ≈ 15 min

Watch first9:37 · IBM Technology

The video is about wrong facts; this part is about wrong structure, but the root cause is the same: the model produces likely output, not checked output. Watch for why fluent text says nothing about whether it's correct. Open on YouTube (human captions).

In HOS 1 you saw that the same prompt can produce different outputs. Until now that mostly affected wording. But when the model produces tool arguments, its output goes straight into your code, and code is not forgiving. The model might send {"expr": "25*4"} instead of {"expression": ...}, an empty string, a number where a string belongs, or a perfectly formed "sqrt(banana)".

The course description calls this "probabilistic logic for handling nondeterministic outputs." In practice it means one habit: treat model output like user input. You wouldn't pass a web form's text straight into a database; don't pass a model's arguments straight into a function. Check them against a schema first: in Python, a Pydantic model that says exactly what shape and values are allowed.

It helps to sort the ways model output goes wrong, because each needs a different defence:

What goes wrongExampleCaught by a schema?
Shape: missing or misnamed field{"expr": "25*4"}Yes
Type: wrong kind of value{"expression": 25}Yes
Rule: right type, not allowed{"text": " "} (blank)Yes, with a validator
Meaning: valid, but not what the user askedUser asked 25 + 4; model sent "25*4"No

The HOS 3 build guards the calculate tool with the simplest possible schema, and the Understand & Refine step adds a rule to a second tool:

class CalculateArgs(BaseModel):
    expression: str                  # must exist, must be a string

class WordCountArgs(BaseModel):
    text: str

    @field_validator("text")
    @classmethod
    def not_blank(cls, v):
        if not v.strip():
            raise ValueError("text must not be empty")
        return v
Worked example

A user types "calculate the square root of a banana." The HOS 2 app passes the model's arguments straight to calculate(), which raises an exception: HTTP 500, and the user sees a generic error. With a schema in front of the tool, a malformed argument is caught before the tool runs, and the app decides what happens next instead of crashing. A stricter schema could go further and allow only digits, operators and parentheses, so "sqrt(banana)" never reaches the tool at all.

⚠ Common mistakes

  • "It worked when I tried it." One success says little about a nondeterministic system. Evaluate with many runs and deliberately awkward inputs.
  • Validating inside the tool instead of before it. By then the bad value is already in your code. Validate at the boundary.
  • Assuming a schema catches everything. It checks shape, type and rules, never meaning.
Quick check

For each, say whether CalculateArgs rejects it: {"expression": "2+2"}, {"expression": 4}, {}, {"expression": "2+2", "note": "hi"}. (Pydantic ignores extra fields by default.)

Part 2 — Guardrails: validate, retry with feedback, fail to data ≈ 5 min

Watch first1:27 · Red Hat

A short overview of guardrails in general: checks placed around a model's input and output. This HOS builds one specific kind, an output check on tool arguments. Open on YouTube (human captions).

A guardrail is code that stands between the model and the rest of your system and decides what gets through. The HOS 3 guardrail has three moves:

model outputtool args
→
validatePydantic schema
→
valid?run the tool
invalidretry, adding the error message
→
up to 2 retrieseach one sees the last error
→
still invalidreturn {"error": …}
def call_with_guardrail(fn, schema, max_retries=2):
    hint = None
    for attempt in range(max_retries + 1):
        raw = fn(correction_hint=hint)          # ask the model (again)
        try:
            return schema.model_validate(raw)   # valid → done
        except ValidationError as e:
            hint = str(e)                       # tell the next attempt what was wrong
    return {"error": "could not get a valid response"}

Simplified. The version in guardrails.py also logs each failed attempt and returns the last error alongside the message.

Three design choices are doing the work. Retrying gives a nondeterministic system another roll. Feeding the error back makes the next roll better than the first; a blind retry tends to repeat the same mistake. And failing to data ({"error": ...}, not an exception) keeps the request alive so the model can explain the problem to the user, like HOS 1's try/except.

Retries aren't free, so it's worth doing the arithmetic. If a call fails validation 30% of the time and attempts are independent, then 70% of requests need one call, 21% need two (fail, then pass), and 9% need all three. That's about 1.4 model calls per request on average, and the share that still fails after three attempts is 0.3 × 0.3 × 0.3 ≈ 2.7%. Feeding the error back usually makes later attempts more likely to pass than the first, so the real numbers tend to be better.

One limit to keep in mind: a schema checks shape, not meaning. If the user asked for 25 + 4 and the model sends "25*4", that passes every structural check. Some mistakes need a lookup, a confirmation step, or a human. You'll sort which is which in the Application Challenge.

Worked example

The model calls word_count with {"text": " "}. Attempt 1 fails not_blank. The guardrail retries and adds the error ("text must not be empty") to the request. Attempt 2 comes back with the user's actual sentence, passes, and the tool runs. Without the hint, attempt 2 sees exactly the same request as attempt 1 and is likely to make the same choice. Without the guardrail at all, the tool would happily report "0 words," a wrong answer with no error anywhere.

⚠ Common mistakes

  • Retrying forever. Always cap retries; an unbounded loop turns one bad request into a stuck server and a large bill.
  • Retrying blind. Without the error message, a retry is just the same request again.
  • Raising instead of returning. An exception after the last retry becomes an HTTP 500. Return a structured error the model can explain.
Quick check

Using the numbers above: if you raise max_retries from 2 to 4, what happens to the share of requests that still fail, and to the worst-case number of model calls per request? When would that trade be worth it?

Part 3 — Async: moving slow work off the request path ≈ 20 min

Watch first15:37 · IBM Technology

The longest video this term, covering more than this part needs. Watch for the three roles (producer, queue, consumer) and why the producer doesn't wait. In this HOS, the API is the producer, Redis holds the queue, and worker.py is the consumer. Open on YouTube (human captions).

Ingesting a document means chunking it and embedding every chunk, easily many seconds for a long file. If POST /documents does that work inside the request, the user waits the whole time, and in a simple server so does everyone else. The fix is to split "accept the work" from "do the work."

Request path: returns in milliseconds
POST /documents
→
enqueue jobRedis (Upstash)
→
{"job_id": …}immediately
Background: a separate process, python worker.py
workertakes the next job
→
chunk + embedinto Chroma
→
statusqueued → started → finished / failed

The HOS 3 code uses RQ (Redis Queue), a small Python library. Enqueuing a job and checking on it are each a couple of lines:

@app.post("/documents")
def upload_document(body: UploadRequest):
    job = queue.enqueue(ingest_document_job, body.doc_path)   # store the job, don't run it
    return {"job_id": job.id}

@app.get("/jobs/{job_id}")
def job_status(job_id: str):
    job = Job.fetch(job_id, connection=redis_conn)
    return {"status": job.get_status(), "result": job.result}

Notice that upload_document never calls ingest_document_job. It only records "someone should run this, with this argument" in Redis. The worker is a separate operating-system process, started in its own terminal, that waits for jobs and runs them. That's why the most common HOS 3 bug is jobs stuck on queued forever: nobody started the worker. Nothing errors. The queue just waits.

The client finds out what happened by polling: asking GET /jobs/{id} every second or two until the status is finished or failed. HOS 4 replaces polling with a push notification, so the user can close the app and still hear when the job is done.

Worked example

Inline: a 40-page PDF takes 25 seconds to ingest, so POST /documents takes 25 seconds, and a student who sends "hi" to /chat meanwhile waits behind it. Queued: POST /documents answers in about 50 ms with a job ID, chat stays instant, and GET /jobs/{id} moves from queued to started to finished about 25 seconds later. The work takes just as long; it just no longer blocks anyone.

⚠ Common mistakes

  • Not starting the worker. Jobs sit on queued forever with no error. Run python worker.py in a second terminal.
  • Changing job code without restarting the worker. The worker loaded the old code when it started; restart it after edits.
  • Sending large data through the queue. Enqueue a path or an ID, not the whole file. The job looks the data up when it runs.
Quick check

You upload three documents and stop the worker after the first finishes. What status does each job show? What happens when you start the worker again?

▶ Rehearse before the build: Open the Guardrails & Queue Simulator. Send 20 requests with the guardrail off, then on. Then upload a document in inline mode and send "hi"; compare the wait with queue mode. Finally, set workers to 0.

New words this week (4)
Nondeterministic output & guardrail
Output that can differ on every run, and a check that validates it, retrying or failing safely when it's wrong.
Schema (Pydantic)
A precise definition of what data is allowed: field names, types, and rules like "not empty."
Queue, worker & job
A waiting line of work (in Redis), a separate process that takes work from it, and one unit of that work with its own ID and status.
Request path
Everything that happens between a request arriving and its response being sent. Slow work on this path makes users wait.

    Concept Debate

    Discussion board · 3 stages
    This week's question

    When a model's output fails validation, should the system keep retrying for a better answer, or fail fast and tell the user?

    You'll argue the side your debate group is assigned, then argue the other one, then drop advocacy and synthesize.

    Your side this HOS

    Sides rotate each HOS. In HOS 3, Debate Group 1 argues Side A and Debate Group 2 argues Side B — the same as HOS 1. Find your group under Communication → Groups in Brightspace. Not in a group? Before posting Stage 1, count the posts on each side and join the side with fewer; if they're tied, take Side A. How sides are assigned →

    Side A — Retry until it's right (within a budget)Group 1 this HOS

    Retry with the validation error fed back, up to a sensible limit, before giving up.

    • Most validation failures are one-off; a second roll with feedback usually succeeds.
    • The user asked for a result, not an error message.
    • A retry costs cents and a second or two; a failed task costs the user's trust.

    Side B — Fail fast and tell the userGroup 2 this HOS

    Validate once; on failure, return a clear error and let the user rephrase or try again.

    • Every retry adds latency and model cost, and multiplies at scale.
    • A model that produced bad output once may be confused by the input — retrying hides that signal.
    • Fast, honest failure is predictable and easy to test.

    Before replying to anyone, post the strongest version of the side you didn't hold.
