HOS 2: Embeddings, Chunking & RAG Pipelines

Extend HOS 1's chat app with retrieval: chunk and embed a set of documents into a vector database, then ground the agent's answers in them — using an AI assistant to scaffold it, then proving you understand what it built.

Est. 2–2.5 hrsOutcome 2Module 2 · Weeks 3–410% of final grade
Before you start Create Evaluate Analyze Understand & Refine Common snags
🧭

Before you start

  1. Check your account setup. This module needs a the same Gemini API key from Module 1. Set it up first; the build won't run without it.
  2. Know the concepts. Read Concept Companion → Module 2 before you open the starter code.

What you'll need

  • Starter code: this HOS's starter-code folder — your HOS 1 app, already working, plus five blank sample documents. Not sure what a file does? See the starter code walkthrough for this HOS.
  • Your HOS 1 API key — same `.env` setup
  • An AI coding assistant available in your environment

This HOS is graded across four stages instead of on code correctness alone: Engagement (Create/Scaffold) is 20% of the HOS grade, and Skills is 80%: Evaluate, Analyze, Apply (the change you make by hand in Understand & Refine) and Understand (your own explanation of it), 20% each. Each stage below says exactly what to submit. Everything goes in your Module 2 GitHub Classroom repo: written work under the matching heading in hos/NOTES.md, screenshots in hos/screenshots/. Commit and push as you go, then submit the repo link to the HOS 2 assignment in Brightspace by the end of Week 4.

🛠️

1 · Create / Scaffold

Graded as Engagement: 20% of this HOS. The AI-assisted starting point, not the deliverable.

Prompt your AI assistant to add retrieval to the existing app:

Add RAG to this app:
- backend/ingest.py: chunk each .md file in backend/sample_docs/ into
  ~400-word pieces and embed them (Gemini's embedding model,
  task_type="RETRIEVAL_DOCUMENT") into a local Chroma collection.
- backend/retrieval.py: a retrieve(query, k=5) function that embeds
  the query (task_type="RETRIEVAL_QUERY") and returns the k nearest
  chunks from that collection.
- Wire retrieve() into backend/agent.py: inject the retrieved chunks
  as a system instruction before the model answers, so it grounds its
  reply in the documents. Keep the existing tool-calling loop working
  alongside this — don't let the new instruction suppress tool use.

Run python ingest.py once the scaffold is in place, then test in the chat app.

Submit (Engagement)
  • The prompt you gave your AI assistant, and a screenshot of the scaffolded app running.
🔍

2 · Evaluate

The critical gate — is the AI-produced result actually correct?

Test it on purpose. At minimum, try:

  • A question only answerable from the sample docs (e.g. "how long do I have to return an item?") — does it cite the real figure, or guess?
  • A question that needs one of your HOS 1 tools (e.g. "what's 25 times 4?") — does it still call the tool, or does the new RAG instruction silently swallow tool use? This is a real, common bug — worth testing even if your app seems fine at a glance.
  • A policy-shaped question the docs don't cover (e.g. "do you offer gift wrapping?") — does it say it doesn't know, or invent a plausible-sounding answer?
Submit
  • A short written note: what you tested, what you found, and anything the AI got wrong, missed, or handled surprisingly well.
🔬

3 · Analyze

Why does this work, mechanically?

Pick one specific piece — a strong choice is why ingest.py and retrieval.py use different task_type values (RETRIEVAL_DOCUMENT vs. RETRIEVAL_QUERY) even though they call the same embedding API. Explain what that setting actually changes and what would happen (not crash — just get quietly worse) if both used the same one.

Submit
  • A short written walkthrough of the one piece you chose, in your own words.
✋

4 · Understand & Refine

The mastery check — can you extend it correctly, without AI doing this part too?

By hand this time — no AI assistance for this stage.

Write a sixth sample document by hand (a new policy or product page, in the same style as the existing five) and re-run ingest.py. Confirm a question that can only be answered from your new document returns the correct, specific detail — proof the full ingest → embed → retrieve path is something you actually understand, not just something you ran once.

Submit
  • A screenshot of the working app, correctly answering a question from your hand-written document.
  • The document itself.
🧯

Common snags

  • Tool calls stop working after adding RAG — check your system instruction's wording. "If the answer isn't in the context, say you don't know" applied broadly will make the model refuse to use tools too. Scope it explicitly to content questions, and say tools are exempt.
  • EMBED_DIM mismatch — the embedding dimensionality has to be identical in ingest.py and retrieval.py, or Chroma's comparison breaks. If retrieval returns nothing useful, check this first.
  • Forgot to re-run ingest.py — after adding your sixth document (Stage 4), the vector database won't know about it until you ingest again.

Most snags trace back to a concept. If one doesn't make sense, see Concept Companion → Module 2.
